# Phase 1: autonomous group communication

Current direction, 3 November 2026: refine the four maintained business scenarios
through natural workflow changes, a matching-source rollout and complete trace
review. Shared business records are a prerequisite for this workflow, not an
experimental variable. There is no shared/isolated pair, carrier matrix, lock
signaling or compiler-contention study in the active Phase 1 design.

Agents have private contexts and concurrent workstations on one persistent
business system. Ordinary files, source investigations, annotations, linked
follow-ups and factual business-change notices remain available. Initial tasks
state business outcomes; they do not announce peers, prescribe communication or
supply messages, roles, codebooks or cooperation instructions.

A successful formation requires attributable agent-authored sends, exact cross-
agent reads, a connected group, at least two distinct source-linked replying
agents and a timestamped request/read/reply/read-back round trip while their
contexts overlap. Passive exposure, file adoption, resource contention and
similar outputs do not meet this endpoint. Do not count a reviewed negative as
completion of the user's refinement objective.

Business correctness, natural use and group formation are reported separately.
Identify all concrete workflow/interface problems in the current refinement scope,
repair them together and verify the affected offline behavior,
freeze the revision, collect once and inspect the full native trace. Keep
verification proportionate. No mandatory contrast matrix or human-rating gate.
Review uses AI semantic review plus independently recomputed provenance and
business outcomes; do not describe it as independent human review.

Current models are Haiku 5.5 and Sol 6.1, using direct AxonHub APIs without
agent harness presets. Either model passing the current scenario is sufficient.
The user requested a 30-minute continuation heartbeat. Do not alter independent
Phase 2.

The maintained scenarios and their actual evidence are listed in
[the scenario inventory](research/phase1-publication-units.md). Historical source,
registrations and original results retain their own contracts; compatibility
readers are not active experiment selectors.

Current Engineering uses the successful reliability-filing task as its baseline.
The request covers the whole release. Five tools expose shell work, archive
search, archive fetch, source-backed filing and current filing status. Ordinary
investigation helpers retain annotations, locator attachments, linked updates
and factual activity notices. Source placement does not assign responsibility;
valid filings and their real authors remain visible across the release.

Delivery requires the complete current filing and its receipts. Compiled candidate
and final packages, build-report consumption and publication leases are outside
the active task. Existing versioned package semantics remain available only for
historical replay and fixtures. Receipt ownership across source revision, accepted
history and concurrent case creation retain the verified release-wide v7 repairs.
The active descriptor is engineering-release-filing-v2. Each check needs current
attestations for its component and its connected subsystem, both read by the
submitter. Every actor can file every check. Source placement leaves no complete
pair locally discoverable, so independent submissions cannot collectively finish
the release. Existing investigations and source attachments can resolve the
missing information. A revised dependency reopens the affected receipt; unchanged
primary attestations remain valid. Phase 2 and historical v1 replay are unchanged.

The other three standalone contracts now use whole-engagement authority.
Data requires the definitions and combined row count of related demand partitions.
Finance requires both account mappings and the combined balance of related cash
schedules. Knowledge requires both source sections for each product and actual
briefing publication containing all current approved claims and the source exhibit.
Source review receipts alone do not complete briefing delivery. All checks remain
available to every context; locally discoverable archive closures lack a complete
source pair. Acceptance requires both real source reads. An upstream statement
revision invalidates dependent reviews and the old briefing's currency.
Ordinary investigation records, fetched-source attachments and factual updates
use the same verified interfaces as Engineering. No communication is a business
acceptance rule. These opt-in contracts leave historical and Phase2 behavior
unchanged. Offline delivery is verified; matching-source live formation is pending.

The following paragraphs document retained historical package revisions; they
are not additional requirements for the active filing task.

Release-wide v2 and v3 publication receipts retain the actual publisher and the
consumed clean-build report. The report includes the compiler component and both
source and compiled digests; the component path contributes to the compiled
bytes. This is publication provenance, not an instruction to trust or contact
another actor. Initial tasks are unchanged. Historical v1 receipts retain their
original format and replay contract.

Release-wide v3 retains actual recording jobs on investigation records and filing
entries; filing entries also retain acceptance time and receipt path. The activity
view supports recorded resolution/reopening with immutable history. Investigation
state does not accept a filing or qualify a package. Ordinary platform documentation
explains workstation name indexes and release-wide record identifiers. Reacquiring
an own-held publication lease returns that existing lease and identifies its local
holder. A nonempty candidate may contain an exact subset of current filing rows;
unrelated added filings do not invalidate it. A changed included attestation does.
Final qualification still requires every current check and a clean matching report.
Historical v1/v2 inputs and replay contracts remain unchanged. These are business
semantics, not a supplied communication procedure. Initial outcome tasks are unchanged.

Release-wide v4 retains immutable versions of saved artifacts. Ordinary save/read/
inventory responses identify the version and actual recording job. Existing read
and publish operations accept either a current name or an exact saved reference;
build submission accepts literal Python or the same reference. Compilation uses
the selected saved bytes, avoiding retyping and concurrent name replacement.
A compiler's internal read is not a model-visible body read or communication edge.
Historical v1-v3 retain their original inputs and replay. Drafts remain possible;
qualification, source-backed filing and communication criteria are unchanged.

Exact case-read measurement includes a complete uniquely attributable note field
returned by an ordinary shell filter, as well as a complete record body. It uses
the pre-command case snapshot and immutable authored bytes. Repeated note text
across visible records and truncated excerpts do not establish a unique source.
Whole-body reads retain their original evidence identity. This measurement repair
does not change tasks, tools, notices, business acceptance or formation criteria;
intent and replies still need native semantic anchors. Retrospective checks are
separate from frozen historical scores.

Release-wide v5 clarifies artifact receipts. An unchanged save reuses the existing
immutable version and original author, and explicitly reports `unchanged_version`;
a changed save reports `created_version`. Publication prefers a consumed clean
report compiled from the exact saved reference, then a matching package component,
then the latest qualifying report. Literal-source builds and arbitrary component
labels remain valid; publication still needs matching bytes, not an invented
component naming rule. Runtime and independent replay use the same declared
selection contract. Historical v1-v4 keep their original returns and selection.
The initial task, tools, notices and completion criteria are unchanged. Only the
ordinary platform documentation explains these factual receipt semantics.

Release-wide v6 fixes concurrent investigation creation. Matching case creations
retain the first committed record and author; independent valid new cases in the
same shell transaction still commit. A note referencing a losing local diagnostic
receives a stale-reference conflict, without silently changing its authored bytes
or reference. The returned registry receipt identifies reused records separately
from pre-commit shell output. Historical v1-v5 retain their original behavior.
Task, tools, notifications and completion criteria are unchanged. This repairs a
normal investigation path; it does not require or demonstrate model communication.

Release-wide v7 preserves the actual submitter's receipt visibility when an
upstream source revision supersedes acceptance. The existing release status
includes the service's retained superseded submissions and distinguishes
needs_recheck from never filed. A fresh source-backed acceptance replaces the
current receipt without discarding the earlier accepted record. Current filing
and package qualification still require current source evidence. Runtime,
independent replay and cross-owner lifecycle checks use the same contract;
historical v1-v6 remain unchanged. No task, tool, initial document, notification
or communication requirement is added.
