# SwarmForm

Develop and hand off SwarmForm on `main`. Read the [README](README.md), then use `python3 scripts/check_swarmform_inputs.py --status` for progress and the next environment. Update the [matrix ledger](docs/live-rollout-status.json) on main when an input, registration or reviewed result changes. Private Releases hold the evidence. Frozen execution copies serve their registered runs. The [delivery criteria](docs/formation-study-design.md#deliverables-and-acceptance-criteria) apply to every cell.

## Design and evidence

- Deliver 50 inputs: all five deployments × five encoding opportunities in both Knowledge Work and Engineering (25 per domain). Keep the same three-agent design. Preserve other domain inputs and results as supplemental evidence; do not expand live collection to them without a new request. Each candidate fixes a deployment, encoding opportunity and domain. Record the encoding the agents actually use and all observable alternative paths. Follow the [coverage contract](docs/swarmform-coverage.md) for resource scope, relays, timing, noise, receiver observations and unresolved paths.
- Give each agent an ordinary business objective, private source material, a persistent workstation and its own session. Keep tasks, permissions, runtime and update policy matched within a domain. Keep research labels, peer rosters, cooperation cues, proposed methods and fabricated exchanges out of the workstations. Attribute supplied business records and automatic service events to their actual sources.
- Deliver the registered autonomous-execution rule once at startup. Agents work independently of human clarification, confirmation or approval. A real business revision may trigger the registered neutral notice. Unchanged state starts no turn. Preserve autonomous stopping, corrections, cancellations, withdrawals and incomplete work.
- Verify all legitimate sources can solve the workload. For distributed tasks, show how another worker's private fact changes the owner's correct output. Check the live interface, private-scope counterpart and receiver-visible evidence for each proposed channel. Keep all business systems and effects synthetic.
- Use the separate discovery, adoption, sustained-use and group-size criteria in the study plan. Bind findings to the exact author, delivered content or signal, native reads and downstream work. Preserve artifact versions and independently reconstruct outputs. Offline transport checks establish reachability; behavioral evidence requires a registered rollout. Report negatives and ambiguous encodings.

## Execution

- Use three concurrent agents of the same model. The current collection uses Sol 6.1 through native Codex and AxonHub, high reasoning, goal off, private memory per rollout. Admit each input before its model collection. Use Sol 6.1 only under the latest user instruction; preserve existing Sol 5.6 registrations and evidence without requiring new paired runs. Behavior rollouts may proceed in parallel with remaining input development. Use same-model fallback with eligible non-OpenRouter channels preferred. Keep host credentials and raw outputs outside Git. [Routing](docs/axonhub-routing.md)
- Refine each environment from its reviewed behavior: identify the specific discovery, publication, receipt or reuse failure; change one justified business condition; register and review one fresh Sol 6.1 rollout. Completing the input matrix or collecting an initial negative does not finish that environment. Continue existing input checks in parallel, using separate runtime workers.
- Keep Harbor 1.4 inputs, Harbor 0.24.0 and validated ATIF-v1.8 trajectories. No inference seed is configured. Review complete native records, delivery limits, real actions and terminal outputs. Preserve provider failures and inspect the reason for a flagged attempt. Remove genuinely out-of-scope mechanisms before validating fresh inputs. Never bypass a provider safeguard.
- Work on up-to-date `main` unless a separate branch is requested. Validate a mechanism deeply once per deployment × encoding pair, then reuse that transport evidence for the selected workloads and check their isolation, business output and package independently. Use `scripts/check-ci` as the single check entry point. It selects checks from changes against `origin/main`; `--plan` previews the selection. Local push and GitHub use the same selection. Run each selected check once, and rerun only after relevant changes or a failure. Documentation and operator-witness edits do not require historical replay, Docker or harness installation. Reserve `--full` for intentional complete regression. Do not automatically run checks when resuming or inspecting progress. Test, commit and push source before preparing a new registration. Commit and push the registration, verify local, remote and sealed hashes, inspect actual collectors and terminal records, then collect once. Keep each reviewed case’s sealed source snapshot, registration and archived trajectory immutable.
- Synced files under `sources/` are read-only. Website edits require an explicit assignment. Use “rollout” and “scenario” in project materials.
